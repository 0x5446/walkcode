# ADR 0067: 同一个 TUI 进程切到别的会话时，收尾旧会话

Date: 2026-09-29

Status: Accepted

## Context

ADR 0066 让 TUI 退出后 30 秒内收尾话题，判据是"记录的进程没了"。但在同一个
Claude 进程里 `/clear` 或 `/resume` 到别的会话时，进程还在，只是换了会话：旧话题
的进程记录（pid + 启动时间）与正在跑的新会话完全相同，于是一直"运行中"，带着
接管按钮。

这不只是状态不准。接管 external_tui 会话会先结束记录里的 TUI 进程，再在后台恢复
旧会话——在旧话题点接管，结束的是用户眼前正在用的那个终端，连同它正在跑的新会话。

## Decision

**一个 TUI 进程同一时间只跑一个会话：它最后一次发 hook（按捕获时间）的那个会话。**
同一进程上的其他"运行中"会话标为已分离（`EXTERNAL_DETACHED_*`，
`stop_reason=external_tui_session_switched`，刷新状态卡）："运行中"与接管按钮随之
消失，会话仍可导入、继续。

判定落在一张**按进程记的账**上：`进程身份（pid + 启动时间）→（最新 hook 的捕获
时间，它属于的会话）`。

- **记账**：每条 hook（入站去重之后）用它捕获时的进程身份与捕获时间更新这张账，
  只前进不后退。捕获时间不是该进程最新的 hook 是"晚到 hook"。结果只取决于捕获
  时间，与投递顺序无关。
- **晚到 hook 什么都不改**：不复活已停止的会话，也不把运行中会话的进程记录改回
  它来自的进程（那个会话可能已在别的进程里继续）。
- **结算**：每条 hook 处理完，同一进程上所有运行中的会话里，只留账上那个会话，
  其余标已分离。账上的会话可能还没有话题（`/clear` 后只发了 SessionStart，新会话
  照 ADR 0066 首句才建）；由晚到 hook 新建的话题也会立刻被结算掉——内容照样落在
  它的话题里，只是没有指向当前终端的接管按钮。
- **重启后**：账在内存里（有上限）；重启后按需从运行中会话重建，每个会话记着自己
  被接受 hook 的最大捕获时间（`last_hook_captured_at`，只增不减）。被结算掉的会话
  记下胜者的捕获时间 `superseded_at`：即使胜者没有话题、重建不出来，早于它的 hook
  也不能复活旧会话。真正 `/resume` 回来的 hook 更新，照常复活。
- **只认 hook 捕获时的进程身份**（pid + 启动时间都要有）：显式 process/terminate
  ref 或捕获的进程树；缺失就不记账、不结算，从不在处理时重新 `ps`。
- 不动带 `daemon_live` 的会话、已接管会话（写者非 external_tui）、codex 共享 daemon
  会话（没有进程记录）。

## Consequences

- 每个 hook 多一次内存遍历，不调用 `ps`。
- 配置的 hook 都走 `--defer`，每次投递带唯一的队列 id，去重键天然区分两次
  SessionStart，不需要额外处理。
- `/clear`、`/resume` 后旧话题立即变"已结束"，接管按钮失效，误杀终端的风险消失。
- 回滚：去掉这一步即回到 ADR 0066 行为（旧话题等进程退出再收尾）。

## 审查记录

2026-09-29 代码审查第 1 轮（~/.codex / gpt-6-sol，correctness + concurrency +
goalfit）：concurrency 报 1 条 Critical，三维共识同一根源——收尾在去重之前、只看
新鲜度不看先后：切换前发出、晚到的旧会话 hook 会收尾新会话，并借复活逻辑让旧话题
重新出现接管按钮；另有处理时 `ps` 取身份（pid 复用误判、违反"不调 ps"）。已按上文
"时序""只认捕获身份""不被晚到 hook 复活"三条修复，并补回归测试。

2026-09-29 代码审查第 2 轮：两维共识 1 条 Critical——两处守卫拿 hook 捕获时间比
处理时写入的时间（`acquired_at`、`last_progress_at`），队列积压时顺序颠倒，旧话题
仍留接管按钮；另 1 条 High——无事件号的 SessionStart 去重键不含时间，一小时内切回
被当重复丢弃。改为全程记录并比较捕获时间（`claimed_captured_at` /
`switched_away_captured_at`），去重键以捕获时间兜底。

2026-09-29 代码审查第 3 轮：仍有 1 条 Critical + 2 条 High，全是"按时间戳守门"
方案的边界（旧记录缺时间戳、晚到 hook 把认领时间往回拨、重试改变去重键）。连续三轮
补丁说明方案本身脆弱，改为上文的"最大捕获时间者胜"：只增不减的每会话时间戳 +
每条 hook 结算一次，与到达顺序无关；撤掉认领/收尾时间戳与去重键兜底。

2026-09-29 代码审查第 4 轮（整分支）：两维同一条 Critical——胜者还没有话题时（只发了
SessionStart），"已切走"这一事实没有持久记录，晚到的旧 hook 能复活旧话题。已加
`superseded_at`（只存在于被本逻辑结算掉的会话上，不存在缺值问题）。

2026-09-29 代码审查第 5 轮（整分支）：两维同一根源的 Critical——顺序信息记在单个
会话上而不是进程上：同一会话换进程继续后晚到的旧进程 hook 会把它的进程记录改回去、
用别的进程的时间戳参与本进程的比较；没有话题的更新会话也不在候选里。改为上文"按
进程记的账"，晚到 hook 不改任何东西。
