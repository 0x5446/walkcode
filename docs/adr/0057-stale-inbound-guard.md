# ADR 0057: 滞留消息时效守卫——过了会话推进点的旧消息不自动提交

Date: 2026-07-20

Status: Accepted; implemented

## Context

飞书对未确认的事件会积压并在重连后原样补推（断连、serve 崩溃期间的消息
一条不少地涌回来）。入站台账只做"同一条不处理两次"的去重，从不判断消息
是否已过时效。于是：断连期间用户在终端把会话推进了十轮，重连后那条滞留
的旧消息照样被自动提交（会话已清扫时甚至触发复活来送它）——语境早已
失效，弊大于利。

用户抠过"时间戳撞车"问题，结论：两个输入面（飞书/终端）没有共享的
发号器，transcript 偏移只覆盖已入会话的内容、无法给迟到消息定位——
跨源排序只能靠时间，用容差把撞车面压到零。

## Decision

- `InboundEvent.created_at`：飞书 `message.create_time`（毫秒→秒），
  缺失为 0；经 `TurnInput.created_at` 透传。
- `Session.last_user_input_at`（持久化）：会话最近一次"被人说话"的时刻。
  频道消息提交成功后记**该消息的渠道产生时刻**（同源同钟——快速连发、
  补推乱序的排序零偏差；若记提交时刻，连发第二条会被误判）；终端输入在
  `user-prompt-submit` hook 记**捕获时刻**（不用排水时刻，defer 队列可能
  晚很多）。无时间戳输入退化为本机当前时间。
- 入站守卫（`handle_inbound_event` 路由到既有会话的分支，先于提交与
  复活）：`created_at > 0` 且比 `last_user_input_at` 早 **5 秒容差**以上、
  且消息自身已滞留 **≥30 秒**（now−created_at）才拦。拦截 = 不提交、
  不复活，lark 回"滞留期间会话已被推进，未自动提交；仍需要请重发"，
  degrade 打点 `stale_inbound_refused`；台账按终局完成（补推不再重复
  处理/重发提示）。边界内一律放行——宁可放过，不可错杀。

## Consequences

- 正常使用零感知：快速连发（同钟有序）、30 秒内的短暂重连、无时间戳
  消息（回调等）全部放行。
- 唯一跨钟比较（频道消息 vs 终端输入）被 5 秒容差 + 30 秒最小滞留双保险
  兜住：边界漏掉的都是"几乎同时发生"的良性并发。
- 新建会话分支不设防（滞留消息开新话题无历史语境可失效）；答复
  AskUserQuestion 的路径由既有代际围栏把守。
- 残留：本机时钟与飞书服务端偏差超过容差（NTP 失效数秒级）时守卫可能
  误拦/漏拦一条——拦有提示可重发，漏了等同现状，均可接受。

## Revision（发版前审查采纳，同版修复）

R1 五项全采纳：①daemon 直写成功也盖频道时间水位，且 TUI 侧回显 hook 在
去重**之后**才盖捕获时间——否则回显的本机时间独占水位，频道后续连发被
误判滞留（构造复现过）；②滞留的 `/takeover` 命令同样被拦（旧控制命令
会改 writer 归属，比旧文本更危险）；③awaiting-other 答复分支加同款守卫
（代际围栏只挡接管后的旧答案，会话被推进但代际未变时挡不住），且被接受
的答案同样盖水位；④时间戳统一规范化：NaN/Infinity/负数/未来值一律视为
未知，水位盖章助手 `_stamp_last_user_input` 同规则兜底（污染水位=后续
全部正常消息被判旧）；⑤补钉子测试：滞留 takeover 拦截、滞留答案不吃
等待、5/30 秒精确边界、毒时间戳不污染水位（875 全绿）。
telegram 生产解析无消息时间戳，守卫实际仅对飞书生效（按范围可接受）。
