## 🔴🔴 顶级必修（9 维度共识，已修复）

### 1. [Warning] `_handle_callback_event` 的 `except Exception` 过宽
- **共识**：correctness/errors/data/observability/design/clarity/extensibility/feasibility/risk 全部命中（Confidence 0.86–0.95）
- **问题**：任意投递异常都被翻成"服务重启过/卡片失效"，且 `NOT_FOUND` 完成入站账本，真实的临时错误不可重试；ask 的本地提示分支失败也会误翻 stale。
- **处置**：✅ 已修——只捕 `TransportUnavailable`；其它异常继续传播（ledger fail 保留重试）。新增测试 `test_non_transport_unavailable_failure_does_not_flip_stale`。

## 🔴 高共识（已修复）

### 2. [Warning] 启动 sweep 无栅栏（errors + feasibility + round2 双维度）
- **问题**：bridge 先启动、sweep 后台跑，首条消息可能撞死 handle 或新会话被误扫；`--once` 入口完全没覆盖。
- **处置**：✅ 已修——sweep 前置为所有 ingress 入口（lark ws / telegram 轮询 / `--once` 经 `poll_telegram_once`）的同步启动栅栏，进程内幂等一次。

## ⚠️ 接受/遗留（明确不在本版修）

- **reverify#1（0.95）**：`decide_from_token` 先落账，非 stale 异常传播后同一 callback 重试会撞 `already_decided`，决策仍可能丢。属既有 decide-then-deliver 架构债；需要两阶段提交或决策回滚，改动面大、触发率低（需非 TransportUnavailable 的投递异常）。**遗留**：后续版本做决策投递两阶段化。
- **concurrency#1**：双 runtime 进程共用同一 state 文件时 sweep 误停对方会话。部署形态为 launchd 单实例，state 本就不支持多进程并发。接受。
- **observability#2**：`refresh_session_status_card` 失败无 degrade 日志。既有行为，非本 diff 引入。遗留。
- **锁公平性**（本轮真机发现）：gate 发卡/flip 在 `_ingress_lock` 内做 Lark 网络 IO，慢调用期间 best-effort 维护任务（outbox flush 5s / defer drain / binding refresh 15s）反复 TimeoutError 推迟。非死锁（下轮自愈），但值得把网络 IO 移出锁。遗留。
